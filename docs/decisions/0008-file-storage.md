# ADR 0008: task files behind a streaming storage port

- Status: accepted
- Date: 2026-09-19

## Context and decision

The task detail design has links, PDFs and images. Links were delivered first and never
cause a server-side URL fetch. Files must work locally now without choosing a cloud vendor.

`application/ports/file_storage.py` defines only `save(key, chunks) -> StoredFile`,
`open(key) -> async iterator`, and `delete(key)`. Use cases depend on this Protocol,
not a path, SDK, HTTP client or storage URL. Keys are independent UUIDs generated by the
server, never client filenames. `STORAGE__PROVIDER` selects a factory in
`infrastructure/storage/registry.py`; `bootstrap.py` composes it. An unknown provider
fails at startup. A new cloud adapter is one adapter file plus one registry entry,
with provider configuration when needed; no use case or route changes.

The local adapter stores files below `STORAGE__LOCAL_DIRECTORY`. Its constructor does
not create directories. Writes are exclusive (no accidental overwrites), mode 0600,
and streamed off the event loop; failed or cancelled writes remove partial files.
Reading reports a missing file before returning the stream. Deletion is idempotent:
a missing key or a directory is a no-op, never recursive deletion. Both adapters run
the same contract suite (`tests/contract/test_file_storage_contract.py`); the disk
adapter additionally has traversal, symlink, disk failure and cancellation tests.
The API's named `attachments-data` volume survives container replacement/rebuild.

## HTTP and validation

- Files arrive as a single multipart `file` part. `api/multipart.py` drives the
  python-multipart parser from `Request.stream()` in bounded chunks, **not** FastAPI's
  fully parsed/spooled `UploadFile`. Headers/envelope overhead have independent bounds;
  truncated bodies, additional parts and oversized envelopes are rejected.
- `AttachFile` buffers at most the signature prefix plus the current stream chunk,
  recognises PDF, PNG, JPEG, GIF and WebP, and checks the configured byte limit during
  consumption (10 MiB by default). Client MIME types and filename extensions do not
  determine type. Empty files are 422, unsupported signatures 415, oversize 413.
- Names are display metadata: basename only, control/bidi characters removed,
  whitespace collapsed, leading/trailing dots removed, at most 255 characters, and an
  extension matching the detected type appended when necessary. File keys never appear
  in responses. Downloads use the stored MIME type, RFC 5987 encoded attachment names,
  and `X-Content-Type-Options: nosniff`. Nothing is statically mounted or executed.
- Every endpoint requires the existing signed-in user seam and rate limiter. Any
  signed-in user can read/change every task, deliberately matching the shared workspace.

## Transactions and limitations

Attachment metadata is stored in PostgreSQL in the task's unit of work. The one new
migration creates only the attachments table; existing tasks/users/projects are unchanged
and start with computed `attachments_count = 0`. Downgrade drops metadata, not task rows;
operators must clear the now-unreferenced files themselves.

An upload takes two short units of work rather than one. `AttachFile` checks the task in
the first, streams the body to the `FileStorage` with none open, and writes the row in the
second. How long a body takes to arrive is the client's choice, so nothing may wait for it
holding a pooled database connection: the upload route therefore takes the task reference
unresolved (`TaskReference`, not `TaskId`, whose key lookup would open the request's
transaction), and the bearer token seam resolves the caller in a unit of work of its own
that ends before the route runs, so no dependency of the request keeps one either.
`tests/unit/test_attach_file.py` and `tests/api/test_file_attachments.py` assert that no
unit of work is open while the storage is being fed, the second through a real token, so
the rate limiter and the signed-in-user seam are exercised too.

`FileChanges` follows a transaction: a rollback (including a failed commit) compensates
newly written files, while a successful commit triggers deferred deletion. The request
scope wraps it around `transactional_session` for removals; an upload wraps it around the
storage write and the unit of work that stores the row, so a file whose row never commits
is deleted whichever of the two failed. Deleting a task locks its row, enumerates file
keys, and cascades the attachment rows; attaching rechecks/locks the task after streaming,
so a slow upload holds no row lock, and a concurrent deletion cannot strand a file.

There is no distributed transaction between PostgreSQL and the filesystem. Process death
between write and commit, or disk failure during cleanup, can leave orphan files. Cleanup
failures are logged without replacing the original exception or misreporting an already
committed transaction. This small local adapter does **not** provide replication, backups,
high availability, cross-host sharing, lifecycle policies, resumable uploads or automatic
orphan reconciliation. Back up both the database and volume; monitor disk capacity and
cleanup warnings. Do not remove files behind the application's back. Database-only task
row deletion by an operator bypasses application cleanup.

## Threats considered and not covered

- Traversal/absolute paths: server-generated keys plus strict ASCII relative-segment
  validation on every adapter operation. Disk descendants are traversed using directory
  descriptors and `O_NOFOLLOW`, refusing symlinks including dangling links; the configured
  root itself may be a trusted volume symlink. An attacker controlling the storage root
  or its ancestors is outside the trust boundary.
- Spoofed MIME/extension and active content: allowlisted leading bytes, safe download
  headers, no SVG, HTML, executable formats, public URLs or static serving. Signature
  checks are **not** full format validation: corrupt/polyglot PDFs/images and embedded
  active content can pass. Downloaded content remains untrusted.
- Memory/disk exhaustion: incremental size enforcement, bounded multipart headers and
  framing, authentication/rate limiting. Connection-pool exhaustion by slow uploads is not
  left to those two: one request per attacker never trips a rate limit, so instead a
  request that is streaming a body holds no database connection at all (see above). No
  aggregate per-user quota or malware scanning.
- Header injection/bidi deception: sanitised names and percent-encoded Content-Disposition.
- SSRF: link URLs are validated but never dereferenced by the API. Credentials in URLs
  and non-http(s)/relative URLs are refused. A link can still lead to an untrusted site.
- Virus scanning, thumbnails/previews, per-user access rules, cloud adapters and encrypted
  object storage are explicitly not covered by this decision.

## What a cloud adapter must implement

Run the shared port contract suite unchanged: preserve exact bytes/size; stream both
ways; reject invalid keys before consuming input; create exclusively; map absence before
reading; delete idempotently; abort multipart/partial uploads on failure or cancellation.
Keep credentials, SDKs and vendor errors in infrastructure; no public object URL escapes
the authenticated content route. Document consistency, durability, cancellation, cleanup
and cost behaviour, and preserve the same transaction compensation semantics.
